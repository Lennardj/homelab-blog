Self-hosted Kubernetes platform

A complete infrastructure pipeline that takes a bare Proxmox host to a running, monitored, TLS-terminated Kubernetes cluster with no manual steps in between.

Source on GitHub →

The pipeline

Terraform  →  provisions VMs on Proxmox, DNS + tunnel on Cloudflare
Ansible    →  bootstraps Kubernetes, installs platform services
Argo CD    →  reconciles workloads from Git, continuously
Cloudflare →  publishes the result with no inbound ports open

What runs on it

  • This website — WordPress with MariaDB, backed by persistent volumes and nightly encrypted backups.
  • Grafana & Prometheus — cluster and node metrics, with alerting to email.
  • Argo CD — the GitOps control plane, itself deployed by the pipeline that it then takes over from.

Engineering decisions worth explaining

DNS-01 certificates, not HTTP-01

Because traffic arrives through a Cloudflare Tunnel, there is no inbound HTTP path for Let's Encrypt to validate against. cert-manager proves domain ownership by writing a TXT record through the Cloudflare API instead. The constraint dictated the design.

A self-hosted CI runner

GitHub-hosted runners are cloud VMs with no route to a private LAN. They cannot reach the Proxmox API or the cluster nodes. A self-hosted runner solves that and keeps every credential off GitHub entirely.

Least privilege at the network layer

A Kubernetes NetworkPolicy restricts the database to accepting connections only from the specific workloads that need it — the web application, the backup job, and the administrative CLI. Every other pod in the cluster is denied, including anything an attacker might land in.

Backups that have actually been restored

Nightly encrypted snapshots with restic to off-cluster storage, with client-side encryption so the backup host never holds readable data. The restore has been performed and verified by comparing row counts against the live database — not merely documented as a procedure.

Failures, written up properly

Every significant failure on this platform is documented with the exact symptom, the diagnostic commands, the hypotheses that turned out to be wrong, and the root cause. A sample:

  • An infinite redirect loop on the admin panel. The reverse proxy was discarding the header the application relied on to detect HTTPS — by design, since forwarded headers are client-controlled and must not be trusted by default.
  • A database that refused to start during a routine update. ReadWriteOnce restricts a volume to one node, not one pod, so a rolling update started a second database process against live data files. The storage engine's file lock was the only thing preventing corruption.
  • A monitoring stack that vanished. Argo CD rebuilt the namespace and ingress but could not rebuild the Helm release, because Helm-managed resources are rendered at install time and never stored in Git. GitOps protects only what is actually in Git.
